When an agent calls a tool on an MCP server, or a function sends a request to an API, something has to authenticate that call. That credential lives in a vault. Subako reads it and attaches it; the model never sees it, and neither does the session log.

## Creating a vault

```ts
const vault = await subako.vaults.create({ display_name: "Support tools" });
```

A vault is a container. What matters is what goes in it.

```ts
await subako.vaults.update(vault.id, { display_name: "Support tools (prod)" });
await subako.vaults.delete(vault.id);
const vaults = await subako.vaults.list();
const support = await subako.vaults.list({ search: "support" });
```

`search` keeps the vaults whose display name holds the term, ignoring case, or whose id does.

## One vault per user

An application that keeps one vault per user names each by `external_id`, its own id for that user, and finds it again by it rather than storing the vault's id. At most one vault in a workspace holds a given `external_id`, so a second create with the same one is refused with a `ConflictError`, and a race between two creates leaves one vault.

```ts
const created = await subako.vaults.create({
	display_name: "Alice",
	external_id: "user_42",
	metadata: { plan: "pro", region: "jp" },
});
const [mine] = (await subako.vaults.list({ external_id: "user_42" })).items;
const pro = await subako.vaults.list({ metadata: { plan: "pro" } });
await subako.vaults.update(created.id, { external_id: null });
```

`metadata` is labels a listing filters by: at most 50 keys of lowercase letters, digits, and underscores, not starting with `subako_`, each holding a string of at most 500 characters. A listing's `metadata` keeps the vaults holding every pair it names. An update's `metadata` replaces them all; its `external_id` sets a new one, or removes it with `null`.

## Adding a credential

```ts
await subako.vaults.addCredential(vault.id, {
	display_name: "Tickets MCP",
	protocol: "mcp",
	target: "https://mcp.example.com/tickets",
	payload: { auth_scheme: "static_bearer", token: process.env["TICKETS_TOKEN"]! },
});
```

**`target` has to match the `url` in the agent's MCP grant exactly.** That is how the broker finds the credential for a call. A mismatch is not an error you get at publish time — it is a tool call that fails at runtime, which is a slower thing to debug.

| `protocol` | Sent to | `auth_scheme` |
| ---------- | ------- | ------------- |
| `mcp` | `target`: the MCP server's exact URL. | `static_bearer` or `oauth` |
| `http` | `origins`: each `https://host` or `https://host:port`, with no path, query, fragment, or user name. | `header`, or `oauth` through [OAuth](#connecting-with-oauth) |

The body's type is a union on `protocol`, so TypeScript takes only the payloads a protocol does; a pairing outside the table is a `400`.

An origin is stored in its one spelling — the host in lowercase, the default port dropped, a trailing `/` removed — so `https://API.example.com:443/` and `https://api.example.com` are the same origin. Plain `http://` is refused unless the deployment lets Core reach the host that way, as a local development stack does for `localhost`. A vault sends at most one credential to an origin: adding a second that names it is a `409`.

## The payload shapes

```ts
// A token you hold
{ auth_scheme: "static_bearer", token: "..." }

// OAuth, where the broker can refresh
{ auth_scheme: "oauth", access_token: "...", expires_at: "2026-10-01T00:00:00Z", refresh: { ... } }

// Headers sent with every request to an http credential's origin
{ auth_scheme: "header", headers: [{ name: "x-api-key", value: "..." }] }
```

`static_bearer` is sent as it stands. `oauth` lets the broker refresh the token when it lapses, so a long session does not die with the credential.

`header` sends each of its `headers` as the request header `name: value`; for a bearer token, that is `{ name: "authorization", value: "Bearer ..." }`. It holds 1 to 16 headers, each name at most once. A name is an HTTP token, compared without regard to case and stored in lowercase, and cannot be one the client or a proxy owns: `host`, `content-length`, `transfer-encoding`, `connection`, `keep-alive`, `te`, `trailer`, `upgrade`, or any `proxy-*`. A value is at most 8192 bytes of visible characters, with spaces or tabs only between them.

## Connecting with OAuth

A credential connected with OAuth does not need you to hold a token at all. Core hands you a URL to send the browser to — a "Sign in with ..." button — and the provider sends the browser back to a page of yours, which finishes the connection:

```ts
// On the button: start, then send the browser away.
const started = await subako.vaults.startOAuth(vault.id, {
	protocol: "mcp",
	target: "https://mcp.example.com/tickets",
	display_name: "Tickets MCP",
	redirect_uri: "https://app.example.com/vaults/oauth/callback",
});
if ("authorization_url" in started) {
	window.location.assign(started.authorization_url);
}

// On the page at redirect_uri: finish, with what the browser came back with.
const query = new URLSearchParams(window.location.search);
const { id } = await subako.vaults.completeOAuth(vault.id, {
	state: query.get("state")!,
	code: query.get("code")!,
});
```

Core presents itself to the provider as an OAuth client. For an MCP server that names its authorization server, Core registers that client on the spot, and you need nothing more. For any other provider — an MCP server whose provider registers no client on the spot, or the API an `http` credential is sent to — the client is one you created at the provider and registered in the workspace as an [OAuth client](#oauth-clients); name it with `oauth_client_id`:

```ts
const started = await subako.vaults.startOAuth(vault.id, {
	protocol: "http",
	origins: ["https://www.googleapis.com", "https://gmail.googleapis.com"],
	oauth_client_id: google.id,
	display_name: "Drive and Gmail",
	redirect_uri: "https://app.example.com/vaults/oauth/callback",
});
```

The URL carries the connection's `state`, which Core keeps only as a hash, so a retried start answers with a [receipt](/reference/timeouts-and-retries#receipts) instead — `expires_at` alone; start again to get a URL.

The result is an `oauth` credential holding what the provider issued, refresh token included when it gave one. An `http` one is sent to each of its origins as `authorization: Bearer ...`, refreshed before a function call whenever it would lapse before the call could end. Only the caller that started a connection can complete it, once, within ten minutes; a `state` that names nothing of yours is a `404`. When the person declines at the provider, the browser comes back with `error=access_denied` instead of a code, and there is nothing to complete.

### OAuth clients

An OAuth client holds what a provider issued when you registered an application with it: its endpoints, the client id, and the client secret. Register `redirect_uri` with the provider too: it sends the browser back only to a URL it knows.

```ts
const google = await subako.oauthClients.create({
	display_name: "Google",
	authorization_endpoint: "https://accounts.google.com/o/oauth2/v2/auth",
	token_endpoint: "https://oauth2.googleapis.com/token",
	client_id: process.env["GOOGLE_CLIENT_ID"]!,
	token_endpoint_auth: { method: "client_secret_post", client_secret: process.env["GOOGLE_CLIENT_SECRET"]! },
	scopes: ["https://www.googleapis.com/auth/drive.readonly", "https://www.googleapis.com/auth/gmail.readonly"],
	authorization_params: [
		{ name: "access_type", value: "offline" },
		{ name: "prompt", value: "consent" },
	],
});
```

`update` changes a client in place, and a new `token_endpoint_auth` rotates its secret: every credential connected through it refreshes with the new one from then on. Its endpoints and `client_id` are fixed once it is created, since the credentials connected through it present their refresh tokens there; for another provider, create another client. A client that a credential was connected through cannot be deleted; delete the credential first. A configured client asks for no RFC 8707 `resource`, since some providers refuse the parameter.

### When the provider stops taking it

Core refreshes an `oauth` credential on its own: a minute before its access token lapses, and once more whenever its server refuses it; an `http` one, before any function call it would not outlast. When the provider refuses the refresh token too — the person revoked access, or the grant expired — the credential is listed with `status: "reconnect_required"`, and sessions stop sending it. Reconnecting takes the person through the provider again, for the same target or origins, name, and client, and puts the new grant in place under the same credential id:

```ts
const started = await subako.vaults.reconnectOAuth(vault.id, credential.id, {
	redirect_uri: "https://app.example.com/vaults/oauth/callback",
});
if ("authorization_url" in started) {
	window.location.assign(started.authorization_url);
}

// On the page at redirect_uri, exactly as for a new connection:
const { id } = await subako.vaults.completeOAuth(vault.id, { state, code }); // id === credential.id
```

Only an `oauth` credential can be reconnected; a `static_bearer` or `header` one is a `400`. A retried reconnect answers with the same receipt a retried start does.

### Checking a credential

`checkCredential` asks the credential's server whether it still takes the credential, the way a session would reach it — an MCP `initialize`, after any refresh the credential is due:

```ts
const { result } = await subako.vaults.checkCredential(vault.id, credential.id);
```

| `result` | Meaning |
| -------- | ------- |
| `connected` | The server took it. |
| `rejected` | The server refused a credential that cannot refresh itself, such as a `static_bearer` token. Nothing is marked. |
| `reconnect_required` | The provider no longer refreshes it, or refused the token a refresh issued. The credential is marked, and stays so until it is reconnected. |

A server that cannot be reached at all is a `400`, rather than a verdict on the credential. So is an `http` credential, which has no server to ask.

## Listing and removing

```ts
const credentials = await subako.vaults.listCredentials(vault.id, { limit: 50 });
await subako.vaults.deleteCredential(vault.id, credentialId);
```

The listing describes the credentials — each with its `status`, `active` or `reconnect_required`, an `oauth` one with the `oauth_client_id` it was connected through, and an `http` one with its `origins` and the names of its `headers` — and does not return the secrets: those went in and do not come back out. A header's value is a secret; its name is not.

## Giving a session access

A vault is not attached to an agent. It is named when the session is created, so the same agent can run against different credentials:

```ts
const created = await subako.sessions.create({
	agent_id: agentId,
	vault_ids: [vault.id],
});
```

That is what lets one agent serve several customers, or the same agent run against staging and production without republishing.
